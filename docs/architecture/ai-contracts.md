# AI contracts

## Provider boundary

The shared domain calls `AiProvider`; it receives normalized domain inputs and returns untrusted suggestion results. It cannot depend on a repository or write local data. Implementations are `MockAiProvider` and `RemoteAiProvider`. Remote calls go to a secure backend; model vendor and credentials remain server-side. Keep transport DTOs in `data/ai/dto`, separate from domain models and presentation state.

## Versioned wire schemas

All request and response envelopes carry a schema version. Unknown extra fields are ignored for forward compatibility; unknown enum values invalidate only the affected proposal field/entry as described below. IDs from the service are correlation identifiers, not local task IDs.

### Extract tasks request

```json
{
  "schemaVersion": "1",
  "requestId": "opaque-client-id",
  "referenceDate": "2026-10-10",
  "timeZone": "Asia/Tehran",
  "locale": "en",
  "text": "Prepare the project update by Friday"
}
```

Reference date and time zone are supplied by the app so relative expressions can be interpreted; absence of sufficient context yields no definite date. Set a product-defined maximum input size (initial proposal: 12,000 Unicode code points) at UI, use case, and backend boundaries; confirm with backend/model constraints before release. Do not silently truncate.

### Extract tasks response

```json
{
  "schemaVersion": "1",
  "requestId": "opaque-client-id",
  "proposals": [{
    "proposalId": "opaque-id",
    "title": "Prepare the project update",
    "description": null,
    "priority": "medium",
    "estimatedDurationMinutes": 45,
    "deadline": { "date": "2026-10-16", "certainty": "interpreted", "sourceText": "by Friday" },
    "subtasks": [],
    "explanation": null,
    "uncertainty": []
  }]
}
```

`priority`: `low | medium | high | unspecified`. Deadline may be absent; it is a date-only ISO-8601 value, with certainty `explicit | interpreted`. `subtasks` are optional strings or typed step proposals. `uncertainty` can identify affected fields and a concise reason. Avoid returning chain-of-thought or sensitive hidden reasoning; explanation is a brief user-facing rationale only. A date with ambiguous timezone/reference or malformed value is omitted and surfaced as needing user input, never converted to a guessed deadline.

### Task breakdown request/response

Request contains `schemaVersion`, `requestId`, parent title/description, existing step titles for context, locale, and optional maximum step count. Response contains the same version/request ID and an ordered list of proposal IDs, titles, optional descriptions, and uncertainty metadata. Existing steps are context only. The app appends only selected suggestions after confirmation and must guard against duplicate titles.

### Daily planning request/response

Request contains version/request ID, local date/time zone, candidate task IDs with title, priority, estimate, deadline, and completion state, plus optional user-configured availability. Response is an ordered list of candidate IDs with short rationale and optional suggested date. It cannot invent clock-time slots; if no working hours are supplied, output is an order recommendation only. The client rejects unknown IDs and duplicates and preserves unreturned eligible tasks outside the suggested order.

## Validation and normalization

1. Enforce response byte/field-count limits and schema version before decode.
2. Decode strictly enough to detect malformed envelopes; tolerate unknown extra keys.
3. Trim titles; reject blank titles, control characters, and titles beyond 200 code points. Cap description at 2,000 code points, subtasks at 20, each step at 200.
4. Accept only recognized priority; unknown enum becomes `unspecified` and is visibly editable, or reject the proposal if core shape is broken.
5. Duration must be null or integer 1–1,440 minutes; invalid values become unset and flagged for review.
6. Deadline must parse as a valid ISO date and not exceed product range; invalid/ambiguous values become unset, not normalized to the nearest date.
7. Normalize likely duplicates by case-folded trimmed title plus similar description; mark the pair for review, never silently merge or discard.
8. Partial responses can produce valid proposals plus an incomplete-response notice. A broken envelope produces an error with retry. Empty proposals are a valid empty result.
9. Store proposal state only in an ephemeral/draft review model until explicit confirmation. Local task IDs and timestamps are generated by the app at confirmation.
10. Cancellation stops presentation work and, where transport supports it, cancels the request. Retry creates a new request ID but preserves source text.

## Error model

`Offline`, `Timeout`, `RateLimited(retryAfter?)`, `BackendUnavailable`, `UnauthorizedOrMisconfigured`, `MalformedResponse`, `UnsupportedSchema`, `InputRejected`, `Cancelled`, `Unknown`. Present actionable, nontechnical language. Never expose raw server payloads. Do not retry automatically in a way that duplicates a billable request. Unauthorized/configuration is not framed as a user credential issue because there is no user auth in MVP.

## Mock provider matrix

`MockAiProvider` exposes deterministic scenario selection in tests/dev configuration: successful extraction, empty result, delayed result, offline/network failure, timeout, malformed envelope, valid partial response, duplicate proposals, and cancellation. It returns fixed fixtures based on scenario rather than random content. Production UI labels mock mode in developer-facing settings/build metadata so examples cannot be mistaken for real AI output.

## Remote provider behavior and privacy

Ktor client sends typed requests to an app-configured backend endpoint over TLS. The backend authenticates/authorizes service use as appropriate, applies size/rate limits, calls the selected model, validates its response, and returns the public schema. No private API key appears in mobile source, resources, distributed build config, crash reports, or logs. The user explicitly starts each analysis; settings explain that the note text is transmitted for that request. Retention and provider data handling must be settled before enabling a production endpoint.
